# 1.2. Інженерний аналіз існуючих аналогів та систем-конкурентів

У межах даного підрозділу проведено порівняльно-системний аналіз трьох програмних рішень, що розв'язують задачі диспетчеризації, оптимізації та управління ресурсами: **Timefold Solver**, **Salesforce Field Service** та **Resource Guru**. Огляд виконано з фокусом на їхню системну архітектуру, мережеві протоколи, механізми забезпечення консистентності даних та критичні обчислювальні обмеження.

---

### 1.2.1. Timefold Solver (f.k.a. OptaPlanner Engine)

#### 1. Архітектурний патерн та масштабованість
Timefold реалізовано як Embedded/Standalone Constraint Optimization Engine з підтримкою мікросервісної та подієво-орієнтованої архітектур (Event-Driven Architecture). Обчислювальне ядро функціонує в середовищі JVM як стейтфул-обчислювач (Stateful Solver), що виконує обробку даних безпосередньо в оперативній пам'яті.

Алгоритми метаевристичного (Tabu Search, Simulated Annealing, Late Acceptance) та локального пошуку (Local Search) належать до категорії CPU-bound та Memory-bound процесів. Горизонтальне масштабування досягається шляхом шардингу обчислювальних задач (Solver Partitioning) та винесення запусків розв'язувача в ізольовані воркер-вузли (Quarkus / Spring Boot Worker Pools у Kubernetes). Збереження стану задачі в пам'яті під час ітераційного пошуку ускладнює безшовне автомасштабування без втрати проміжного стану оптимізації.

#### 2. Протоколи передачі даних та міжсервісна взаємодія
* **gRPC / HTTP/2:** Використовується для високоефективної передачі бінарних серіалізованих даних (Protocol Buffers) між API-шлюзом та обчислювальними воркерами під час передачі великих об'єктних моделей задач.
* **REST API (OpenAPI / JSON):** Стандартний інтерфейс для синхронного налаштування параметрів оптимізації, передачі вхідного вектора сутностей та отримання підсумкового розкладу.
* **Asynchronous Messaging (Kafka / RabbitMQ):** Застосовується для асинхронного відправлення задач на розв'язання (`SolveJob`) та потокового отримання проміжних кращих рішень (Best Solution Events).

#### 3. Стек даних та механізми консистентності
* **In-Memory Score Director:** Основні операції над об'єктним графом обмежень здійснюються в RAM.
* **Relational Persistence Layer:** Для персистентного збереження вхідних даних та розрахованих графіків використовуються ACID-сумісні SQL СУБД (PostgreSQL, Oracle) через ORM-шари (Hibernate/JPA) із застосуванням песимістичних або оптимістичних блокувань (`@Version`).
* **Консистентність:** У процесі розв'язання консистентність контролюється алгоритмом дельта-перерахунку оцінки (`Incremental Score Calculation`), що запобігає повному перерахунку графа обмежень при локальних мутаціях (`Move`).

#### 4. Інженерні обмеження та технічні вузькі місця (Technical Bottlenecks)
* **High Memory Overhead & Garbage Collection Latency:** Оперування мільйонами тимчасових об'єктів у пам'яті під час виконання CP/Metaheuristics алгоритмів призводить до затримок, спричинених паузами збірника сміття (JVM GC Pauses), що перешкоджає досягненню Sub-second Latency.
* **Тривалість холодного старту (Cold Start & Warmup):** Потрібен додатковий часовий ресурс для прогріву JVM та побудови початкового графа залежностей.
* **Складність формалізації неперервних інтервалів:** Моделювання розріджених часових діапазонів із динамічною зміною місткості суб-ресурсів вимагає ручного проектування `Shadow Variables`, що підвищує обчислювальну складність і знижує швидкість сходимості.

### 1.2.2. Salesforce Field Service (FSL Optimization Engine)

#### 1. Архітектурний патерн та масштабованість
Salesforce Field Service є складовою Multi-tenant Cloud SaaS Platform з комбінованою архітектурою: монолітне ядро обробки метаданих та розподілений мікросервісний контур оптимізації (Scheduling Service/Engine).

Система орієнтована на обробку асинхронних пакетних задач (Batch Optimization) та локальних оперативно-потокових корекцій (In-jeopardy Scheduling). Горизонтальне масштабування обмежене ресурсолімітами мультитеннатної платформи (Governor Limits), що вимагає декомпозиції великих територіально-темпоральних графів на окремі оптимізаційні горизонти (Service Territories).

#### 2. Протоколи передачі даних та міжсервісна взаємодія
* **REST API & GraphQL API:** Використовуються для виконання CRUD-операцій над ресурсами, отримання системних метрик та інтеграції із зовнішніми ERP/CRM-системами.
* **Salesforce Streaming API (Bayeux Protocol / CometD / Pub/Sub API via gRPC):** Забезпечує реактивну трансляцію асинхронних мутацій розкладу, статусів виконання та геолокаційних подій на клієнтські термінали у режимі реального часу.

#### 3. Стек даних та механізми консистентності
* **Relational Multi-tenant Storage:** Базується на розподілених реляційних сховищах (Oracle / Custom Distributed SQL Databases) із метаданими заповнення об'єктів.
* **In-Memory Caching:** Модулі Redis / Memcached для тимчасового кешування геопросторових індексів та робочих графіків ресурсів.
* **Механізми консистентності:** Реалізовано багаторівневий механізм транзакцій з оптимістичним контролем конкурентності (OCC). При одночасній модифікації графіків декількома диспетчерами застосовується серіалізація через транзакційні блоки Apex та суворе холдування об'єктів (Record Locking).

#### 4. Інженерні обмеження та технічні вузькі місця (Technical Bottlenecks)
* **High Latency при перерахунку розкладу:** Перепланування складного багатофазного графа ресурсів виконується в асинхронному режимі Batch Processing і триває від кількох секунд до десятків хвилин, що унеможливлює реалізацію Sub-second OLTP-бронювань.
* **Платформні обмеження (Governor Limits):** Жорсткі ліміти на час виконання транзакцій, обсяг вибірки SOQL-запитів та використану оперативну пам'яті обмежують гнучкість реалізації власної математичної лексикографічної оптимізації.
* **Висока вартість обчислювальної інфраструктури:** Хмарна закрита SaaS-архітектура робить масштабування під високі пікові навантаження неекономічним для вузькоспеціалізованих застосунків.

### 1.2.3. Resource Guru

#### 1. Архітектурний патерн та масштабованість
Resource Guru реалізовано за патерном Web-based Service-Oriented Architecture (SOA) / Modular Monolith із винесеними асинхронними воркерами для обробки фонових завдань і кешування.

Система масштабується для веб-візуалізації та перевірки вільних слотів (Read-heavy workload). Однак при обробці конфліктних інтервалів у режимі реального часу під час пікових навантажень (Write-heavy workload) виникає вузьке місце в центральній базі даних через високе навантаження на перевірку перетинів часових відрізків.

#### 2. Протоколи передачі даних та міжсервісна взаємодія
* **REST API (JSON over HTTP/S):** Основний синхронний протокол для взаємодії веб-клієнтів та зовнішніх систем із серверною частиною.
* **WebSockets / Long Polling:** Використовуються для трансляції актуального стану таймлайну та сповіщення диспетчерів про зміни у розкладі в реальному часі.

#### 3. Стек даних та механізми консистентності
* **Relational SQL СУБД:** Використовує PostgreSQL / MySQL для збереження сутностей проєктів, броньованих інтервалів та ресурсів.
* **In-Memory Data Store (Redis):** Застосовується для кешування доступності ресурсів, сесійних даних та як брокер черг завдань (Sidekiq / Background Workers).
* **Консистентність даних:** Забезпечується стандартними ACID-транзакціями на рівні SQL СУБД із застосуванням умовних перевірок та індексів B-Tree / BRIN.

#### 4. Інженерні обмеження та технічні вузькі місця (Technical Bottlenecks)
* **Спрощена дискретна модель даних (No Multi-phase Process Decomposition):** Відсутня підтримка формалізації складних процесів у вигляді графів із розщепленням на активні та пасивні фази. Бронювання розглядається як монолітний часовий блок, що призводить до простоїв суб-ресурсів.
* **Вразливість до станів гонитви (Race Conditions under High Concurrency):** Відсутність вродженої індексації темпоральних діапазонів на рівні СУБД (`tstzrange` + `EXCLUDE USING gist`) змушує виконувати перевірки перетинів на прикладній мові (Application Level), що призводить до аномалій подвійного бронювання (Phantom Bookings) при паралельних запитах.
* **Відсутність математичного Optimization Engine:** Перевірка доступності слотів виконується за принципом Booking Validator без автоматичного синтезу оптимального розкладу (Constraint Satisfaction Engine).

### 1.2.5. Аналітичний висновок підрозділу 1.2

Проведений системно-інженерний аналіз існуючих аналогів свідчить про наявність суттєвих архітектурних і функціональних обмежень у сучасних рішеннях диспетчеризації та оптимізації ресурсів. Ключовий недолік розгляданих платформ полягає у використанні спрощеної неподільної моделі часових інтервалів (Resource Guru) або у високій затримці обчислень (Salesforce Field Service), де пакетне перепланування в режимі асинхронного Batch Processing унеможливлює забезпечення субсекундного відгуку ($Latency \le 1000$ мс) при високій частоті OLTP-транзакцій. Крім того, традиційні підходи до перевірки сумісності та виключення перетинів інтервалів на прикладній мові програмування (Application Level) або за допомогою песимістичних розподілених блокувань СУБД викликають суттєву деградацію пропускної здатності (RPS) та створюють ризики станів гонитви (Race Conditions) і виникнення фантомних бронювань при паралельному доступі. Рішення класу Timefold Solver, хоч і забезпечують потужний математичний апарат локального пошуку, вимагають значних ресурсів JVM та супроводжуються затримками через паузи збірника сміття (Garbage Collection), що ускладнює їх гнучку інтеграцію в легкі мікросервісні контури.

Обраний у межах кваліфікаційної роботи технологічний стек та архітектурні патерни ефективно ліквідують зазначені технічні вузькі місця. Застосування асинхронного фреймворку FastAPI у поєднанні з математичним розв'язувачем Google OR-Tools (CP-SAT Core) та його ізоляцією у dedicated воркер-пулі (Task-Worker Pattern через Taskiq та Redis) дозволяє відокремити CPU-інтенсивну оптимізацію від основного I/O-потоку Web API. Гарантія транзакційної цілісності та конкурентного захисту від колізій вирішується без важких блокувань на рівні реляційної алгебри СУБД PostgreSQL шляхом індексації темпоральних діапазонів (`tstzrange`) із використанням обмежень взаємного виключення (`EXCLUDE USING gist`). Усунення аномалій дуального запису (Dual-Write Problem) та забезпечення реактивної синхронізації графіків у режимі реального часу досягається реалізацією патерну Transactional Outbox у зв'язці з брокером Redis Pub/Sub та протоколом Server-Sent Events (SSE).

Таким чином, пропонований інженерний підхід забезпечує баланс між високою обчислювальною точністю розв'язання NP-важкої задачі RCPSP та низькою часовою затримкою відгуку сервісу, гарантуючи розширюваність, відмовостійкість та надійність системи. Сформована концепція слугує алгоритмічною та технологічною основою для наступного етапу розробки — системного проєктування архітектури та специфікації міжсервісних контрактів у Розділі 2.

## 1.5. Модель To-Be, функціональні та нефункціональні вимоги

### 1.5.1. Концептуальна модель To-Be
У цільовій моделі (To-Be) кожна композитна послуга декомпозується на спрямований ациклічний граф (DAG) з активними та пасивними фазами. Ізоляція CPU-bound обчислень реалізується через воркер-пули (Taskiq/Redis), перевірка часових колізій виконується на рівні реляційної алгебри СУБД PostgreSQL (`tstzrange` + `EXCLUDE USING gist`), а реактивна трансляція мутацій забезпечується патерном Transactional Outbox у зв'язці з Redis Pub/Sub та Server-Sent Events (SSE).

### 1.5.2. Перелік функціональних вимог (Core Features)
* **Multi-Phase Process Decomposition:** Формалізація послуг у вигляді ациклічних графів (DAG) з активними та пасивними фазами.
* **CP-SAT Optimization Core:** Синтез розкладів у Google OR-Tools за лексикографічним вектором критеріїв.
* **Baseline Interval Engine:** Порівняльний аналізатор на основі інтервальних дерев (`portion`, `intervaltree`).
* **Range-Level Concurrency Control:** Фіксація темпоральних діапазонів у PostgreSQL (`tstzrange` + `EXCLUDE USING gist`).
* **Hold Lifecycle Manager:** Двоетапне бронювання з тимчасовим фіксуванням слотів ($N$ хвилин, TTL) через Taskiq.
* **SSE Event Broadcaster:** Потокова трансляція мутацій розкладу підключеним клієнтам за патерном Transactional Outbox.
* **Interactive Dispatcher Grid:** Багатодоріжковий таймлайн із підтримкою Drag-and-Drop та автоперерахунком залежностей.

### 1.5.3. Нефункціональні вимоги (NFRs)
* **Продуктивність:** REST API $Latency \le 100$ мс ($p_{95}$) при 500 RPS; CP-SAT Solver $Latency \le 1000$ мс ($p_{95}$).
* **Безпека:** JWT RS256 (OAuth 2.0 / OIDC), PII-знеособлення (GDPR, UUID у CP-SAT), відповідність OWASP Top-10.
* **Надійність:** $0\%$ подвійних бронювань (Phantom Bookings), At-least-once доставка подій через Transactional Outbox, мультиконтейнерний контур Docker Compose, автоматизація CI/CD (`Hypothesis`, `testcontainers-python`, `k6`, `mypy` strict mode).
