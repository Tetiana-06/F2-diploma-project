# ADR-001: Вибір механізму контролю конкурентного доступу та забезпечення ACID-інваріанта неперетину темпоральних інтервалів

* **Status:** Approved (Затверджено)
* **Date:** 2026-11-12
* **Deciders:** Chief Architect (Таня Шостак), Core Backend Team
* **Technical Domain:** Relational Core & Concurrency Control Layer
* **Matching SRS Requirements:** SRS-FUN-DB-01, SRS-NFR-REL-01, SRS-NFR-PERF-01

---

## 1. Context (Контекст та інженерна проблема)
Підсистема виконує розрахунок та бронювання композитних багатофазних послуг. Відповідно до вимог специфікації **SRS-NFR-REL-01**, система повинна забезпечувати $0\%$ фантомних та подвійних бронювань (Phantom Bookings) в умовах пікового конкурентного навантаження до $500$ RPS (**SRS-NFR-PERF-01**). 

У традиційних CRM-системах перевірка вільного часу здійснюється на прикладному рівні (Application Level Validation: `SELECT` вільних вікон $\to$ `INSERT` запису). Під навантаженням High Concurrency між перевіркою та фіксацією виникає часова дельта (Race Condition Window), що призводить до колізій. Необхідно затвердити інфраструктурний механізм взаємного виключення часових інтервалів, який гарантує транзакційну цілісність без введення важких песимістичних блокувань (Pessimistic Table Locks), що деградують швидкодію Web API.

---

## 2. Alternatives Considered (Розглянуті альтернативи)

### Альтернатива 1: Розподілений менеджер блокувань в пам'яті (Redis Distributed Lock / Redlock Algorithm)
* **Опис:** Перевірка та блокування інтервалів виконується в пам'яті In-Memory брокера Redis із використанням атомарних ключів з обмеженим терміном дії (TTL) або реалізацією алгоритму Redlock.
* **Технічна критика та обмеження 2026 року:**
  * Вразливість до аномалій синхронізації системних годинників (Clock Drift / NTP Asymmetry), що спричиняє передчасний знімальний таймаут блокування під час паузи Garbage Collection або асинхронних I/O затримок воркера.
  * Відсутність ACID-гарантій цілісності даних у випадку збою вузла Redis (Master-Replica Failover), оскільки асинхронна реплікація Redis може втратити ключ блокування, викликаючи аномалію Dual-Write та виникнення фантомних бронювань під навантаженням.

### Альтернатива 2: Декларативний захист на рівні реляційної алгебри СУБД (PostgreSQL `tstzrange` + `EXCLUDE USING gist`)
* **Опис:** Часові межі фаз послуг зберігаються у вигляді діапазонного типу даних `tstzrange` (`timestamp with time zone range`). На рівні схемних обмежень PostgreSQL накладається декларативний інваріант взаємного виключення `EXCLUDE USING gist (resource_id WITH =, booking_period WITH &&)`.
* **Технічний аналіз:** Валідація перетинів виконується всередині транзакційного ядра СУБД за допомогою узагальненого індексного дерева (GiST) із часовою складністю $O(\log N)$. При спробі перетину СУБД атомарно відкочує транзакцію та повертає статус помилки `23P01 (exclusion_violation)`.

---

## 3. Decision (Обґрунтоване рішення)
Прийнято рішення затвердити **Альтернативу 2: PostgreSQL `tstzrange` з обмеженням `EXCLUDE USING gist`** за допомогою розширення `btree_gist` як базовий інваріант контролю конкурентності.

### Інженерне обґрунтування вибору:
1. **Математична гарантія ACID-цілісності:** Контроль перетинів перенесено безпосередньо у транзакційне ядро СУБД, що виключає ризик станів гонитви (Race Conditions) на 100%, задовольняючи вимогу **SRS-NFR-REL-01**.
2. **Усунення аномалій Dual-Write:** Відпадає потреба в синхронізації зовнішнього стану Redis з БД перед записом.
3. **Передбачувана швидкодія:** Використання GiST-індексу забезпечує субсекундну перевірку за $O(\log N)$, виключаючи необхідність песимістичного блокування всієї таблиці (`LOCK TABLE`).

---

## 4. Consequences & Trade-offs (Оцінка наслідків та компромісів)

### Позитивні наслідки (Positive Consequences):
* **Гарантоване усунення колізій:** Повне досягнення $0\%$ Phantom Bookings під піковим навантаженням.
* **Спрощення кодової бази бекенду:** Зменшення технічного боргу завдяки відсутності складних механізмів обробки спин-локів на рівні Python-коду.
* **Підтримка нативного часового поясу:** Тип `tstzrange` автоматично обробляє нормалізацію UTC та переходи часових поясів.

### Негативні наслідки та обчислювальний борг (Negative Consequences & Trade-offs):
1. **Зростання навантаження на I/O та CPU СУБД:** Індексація GiST через розширення `btree_gist` вимагає на 20–30% більше ресурсів CPU та накопичувача під час операцій `INSERT/UPDATE` порівняно із класичними B-Tree індексами.
2. **Складність схематичних міграцій (DDL Complexity):** Виконання міграцій Alembic для таблиць із обмеженнями `EXCLUDE USING gist` вимагає короткочасного песимістичного блокування таблиці, що ускладнює проведення Zero-Downtime Deployments без спеціалізованих патчів міграцій.
3. **Необхідність обробки повторних спроб (Retry Policy):** При перетині бронювань СУБД повертає відмову транзакції (Error `23P01`). Бекенд-сервіс (FastAPI / `asyncpg`) зобов'язаний реалізовувати паттерн *Exponential Backoff Retry*, що збільшує утилізацію пулу з'єднань БД при високій конкурентності.
