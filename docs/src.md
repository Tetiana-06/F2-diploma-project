# Software Requirements Specification (SRS)

**Назва проєкту:** Підсистема динамічного планування та оптимізації багатофазних процесів у б'юті-індустрії  
**Стандарт:** ISO/IEC/IEEE 29148:2018  
**Версія:** 1.0-RELEASE  

---

## 1. System Context (Контекст системи)

Підсистема є автономним обчислювально-аналітичним ядром класу **Constraint Satisfaction & Optimization Engine**, що призначене для інтеграції в enterprise-платформи управління ресурсами.

* **Scope системи:** Асинхронний прийом REST-запитів, декомпозиція складених послуг у спрямовані ациклічні графи (DAG), ізольоване розв'язання NP-важкої задачі RCPSP у воркер-пулах, діапазонний транзакційний захист інтервалів у СУБД та потокове реактивне транслювання стану клієнтам.
* **Зовнішні інтеграції:** Клієнтські веб-додатки (Vue.js 3), диспетчерські консолі управління, реляційне сховище PostgreSQL 16+ та брокер Redis.

## 2. Functional Requirements (Функціональні вимоги)

### 2.1. Модуль автентифікації та контролю доступу (AUTH)
* **SRS-FUN-AUTH-01:** Система повинна здійснювати автентифікацію користувачів за протоколами OAuth 2.0 / OIDC із видачею пар підписаних токенів Access (JWT RS256, TTL 15 хв) та Refresh (TTL 7 днів).
* **SRS-FUN-AUTH-02:** Система повинна забезпечувати авторизацію запитів на основі ролей (RBAC: Client, Master, Dispatcher, Admin), повертаючи статус `403 Forbidden` при спробі несанкціонованого доступу.

### 2.2. Модуль декомпозиції та граф-моделювання (DAG)
* **SRS-FUN-DAG-01:** Система повинна формалізувати кожну композитну послугу у вигляді спрямованого ациклічного графа залежностей (DAG), розділяючи етапи на активні фази (блокування виконавця) та пасивні технологічні інтервали (вивільнення виконавця із збереженням локації клієнта).
* **SRS-FUN-DAG-02:** Система повинна валідувати коректність графа послуги на відсутність циклів перед передачею в обчислювальне ядро.

### 2.3. Алгоритмічне ядро оптимізації (SOLV)
* **SRS-FUN-SOLV-01:** Система повинна генерувати безшовний таймлайн візиту за допомогою розв'язувача Google OR-Tools (CP-SAT Core) із формулюванням опціональних інтервалів (`NewOptionalIntervalVar`) та констрейнтів неперетину (`AddNoOverlap`).
* **SRS-FUN-SOLV-02:** Система повинна здійснювати лексикографічну оптимізацію за векторною цільовою функцією: мінімізація загального вікна перебування $\to$ мінімізація ротації персоналу $\to$ мінімізація дельти від бажаного слоту.
* **SRS-FUN-SOLV-03:** Система повинна реалізовувати асинхронний time-budgeting (ліміт 800 мс) із фоновим переключанням на евристичний аналізатор інтервальних дерев (`portion` / `intervaltree`) у випадку вичерпання часового ліміту.

### 2.4. Сервіс транзакційного контролю колізій (DB)
* **SRS-FUN-DB-01:** Система повинна фіксувати часові інтервали у СУБД PostgreSQL із використанням типів `tstzrange` та обмежень взаємного виключення `EXCLUDE USING gist`.
* **SRS-FUN-DB-02:** Система повинна виконувати двоетапне бронювання із підтримкою тимчасового холдування слотів (TTL 10 хвилин) та автоматичним асинхронним вивільненням через черги задач Taskiq при відсутності підтвердження.

### 2.5. Реактивний сервіс трансляції станів (STREAM)
* **SRS-FUN-STREAM-01:** Система повинна публікувати події мутації розкладу у брокер Redis Pub/Sub із дотриманням патерну Transactional Outbox для усунення аномалій Dual-Write.
* **SRS-FUN-STREAM-02:** Система повинна транслювати мутації розкладу підключеним клієнтам у режимі реального часу за допомогою специфікації Server-Sent Events (SSE).

## 3. Non-Functional Requirements (Нефункціональні вимоги)

| Ідентифікатор | Категорія | Опис вимоги та числовий індикатор |
| :--- | :--- | :--- |
| **SRS-NFR-PERF-01** | Performance | Затримка відгуку Web API ($p_{95}$) для CRUD-операцій не повинна перевищувати $100$ мс при навантаженні $500$ RPS. |
| **SRS-NFR-PERF-02** | Performance | Час виконання оптимізаційного запиту CP-SAT солвером ($p_{95}$) не повинен перевищувати $1000$ мс з урахуванням time-budgeting. |
| **SRS-NFR-SEC-01** | Security | Передача даних має здійснюватися виключно через шифроване з'єднання TLS 1.3 з автентифікацією JWT RS256. |
| **SRS-NFR-SEC-02** | GDPR Compliance | Пейлоади задач у воркер-пулах CP-SAT повинні містити виключно знеособлені ідентифікатори (UUID) без збереження PII. |
| **SRS-NFR-REL-01** | Reliability | Система повинна забезпечувати $0\%$ подвійних бронювань під час випробувань на паралельну конкурентність. |
| **SRS-NFR-REL-02** | Fault Tolerance | Система повинна автоматично відновлювати обробку подій після збою Redis за рахунок повторних читань із таблиці Outbox. |
| **SRS-NFR-DEVOPS-01** | Infrastructure | Контейнеризація всіх компонентів через Docker Compose з лімітами ресурсів ($CPU \le 2.0$, $RAM \le 1\text{ GB}$ на воркер). |

## 4. Verification Criteria (Критерії верифікації вимог)

* **SRS-FUN-AUTH-01 / SRS-NFR-SEC-01:** Верифікується автоматизованими інтеграційними тестами `pytest-asyncio` з перевіркою валідності JWT-підпису та скануванням інфраструктури інструментом **Trivy**.
* **SRS-FUN-SOLV-01 / SRS-NFR-PERF-02:** Верифікується навантажувальним сценарієм Spike Testing в утиліті **k6** із контрольним вимірюванням метрики `http_req_duration{p95} <= 1000ms`.
* **SRS-FUN-DB-01 / SRS-NFR-REL-01:** Верифікується Property-based тестуванням алгоритмічних інваріантів у **Hypothesis** та інтеграційним тестуванням паралельних транзакцій у контейнерах PostgreSQL через **testcontainers-python**.
* **SRS-FUN-STREAM-01 / SRS-NFR-REL-02:** Верифікується імітацією обриву з'єднання з Redis у pytest з перевіркою повторного вичитування записів із таблиці Outbox.
* **SRS-NFR-DEVOPS-01:** Верифікується статичним аналізом `mypy` (strict mode), лінтером `Ruff` та автоматичним запуском Docker Compose у GitHub Actions CI.

## 5. Glossary (Глосарій)

* **CP-SAT Solver:** Математичний розв'язувач задач програмування в обмеженнях (Constraint Programming) у складі бібліотеки Google OR-Tools, який використовує сатисфіабільність формул для оптимізації.
* **Resource-Constrained Project Scheduling Problem (RCPSP):** Клас NP-важких задач комбінаторної оптимізації, орієнтованих на складання розкладу виконання робіт з урахуванням обсягу ресурсів та часових залежностей.
* **`tstzrange` & GiST:** Діапазонний тип даних у PostgreSQL (`timestamp with time zone range`) та узагальнене індексне дерево (Generalized Search Tree), що дозволяють реалізувати обмеження взаємного виключення перетинів часу на рівні ACID.
* **Transactional Outbox Pattern:** Патерн проєктування розподілених систем, що забезпечує атомарне збереження стану сутності та події про це в одній транзакції СУБД для запобігання аномаліям Dual-Write.
* **Server-Sent Events (SSE):** Протокол однонапрямного реактивного потокового транслювання подій від сервера до клієнта у режимі реального часу через стандартне HTTP-з'єднання.
* **Taskiq:** Сучасний асинхронний розподілений брокер та менеджер виконання фонових завдань для Python-екосистеми з підтримкою Redis та Task-Worker патерну.
